# Benchmarking with Suvix (Milestone 8)

Benchmarking is central to Suvix's purpose (SUVIX_PLAN.md §16): it answers
whether Suvix's orchestration improves correctness, schema compliance,
timestamp accuracy, cost per correct result, latency, and developer effort
*relative to measured baselines* — never relative to invented numbers.

## The research question

For a fixed video, task, schema, and evaluation criterion, does Suvix
improve each dimension separately? The harness reports every dimension on
its own; it never collapses them into a single score that hides
trade-offs.

## Baselines (plan §16.2)

| Baseline | What it runs | Status |
|---|---|---|
| `A_direct_native` | Direct adapter `extract()` call with the same video, schema, and instructions — bypassing Suvix orchestration. Measures raw provider capability. | Runnable |
| `B_suvix_native` | `Suvix().extract` with `strategy="native_video"`. | Runnable |
| `C_suvix_frames` | `Suvix().extract` with `strategy="selected_frames"`. | Runnable |
| `D_suvix_coarse_to_fine` | Coarse-to-fine workflow (`selected_frames`, `max_refinement_rounds=2`). | Runnable |
| `E_direct_frames` | Direct adapter call with locally sampled frames (the same uniform plan C uses). Optional; skipped honestly for adapters without image input. | Runnable |

A baseline that cannot run (missing video file, inapplicable adapter, adapter
error) produces a `BaselineResult` with `result=None`, `error` set, and a
`comparability_notes` entry explaining why — never silently substituted or
scored as zero.

## Quickstart

```python
import asyncio, json
from pathlib import Path
from suvix.evaluation.runner import BenchmarkTask, run_baseline, summarize

def factory(baseline):  # inject your real adapter here
    from my_adapters import GeminiExtractor
    return GeminiExtractor(model="gemini-2.5-flash")

async def main():
    tasks = [BenchmarkTask(**json.loads(p.read_text()))
             for p in sorted(Path("benchmarks/tasks").glob("*.json"))]
    results = [await run_baseline(t, "B_suvix_native",
                                  extractor_factory=factory,
                                  output_dir="benchmarks/results")
               for t in tasks]
    print(json.dumps(summarize(results), indent=2))

asyncio.run(main())
```

Real-provider runs need API keys and network; keep them out of the default
test suite (`uv run pytest` never touches the network).

## Task format

Tasks live in `benchmarks/tasks/*.json` and validate against
`BenchmarkTask`:

- `task_id`, `category` (`temporal_events` | `objects_counts` |
  `visible_text`), `instructions`, `schema` (Draft 2020-12), `expected`
- `video_path` (bundled video) **or** `video_ref` + `video_sha256`
  (documented external reference)
- `time_tolerance_seconds` (default 1.0), `evaluation_notes`,
  `known_ambiguities`

Expected-output shapes per category (what the runner reads):

- `temporal_events`: `expected.events` = list of
  `{"type": str, "timestamp_seconds": float}`; predicted from
  `result.data["events"]`.
- `objects_counts`: `expected.counts` = `{label: int}`; predicted from
  `result.data["counts"]`.
- `visible_text`: `expected.texts` = `{field: text}`; predicted from
  `result.data[field]`.

The seven shipped tasks use synthetic videos generated by
`benchmarks/fixtures/generate.py` (ffmpeg `drawtext`/`drawbox` — no model
involved). Expectations are annotated from the generation parameters, and
each task records the fixture's sha256. These fixtures validate the
**harness**, not provider accuracy: they are too easy and too few to
support any accuracy claim. Videos are gitignored (`*.mp4`); regenerate
with the script, don't commit binaries.

The original three (`temporal_flashes`, `objects_counts`, `visible_text`)
are static or single-window tasks. Four more exist specifically to defeat
shortcuts and measure failure modes honestly (the TVBench lesson: a task
a single frame can solve does not measure video understanding):

| Task | What it stresses |
|---|---|
| `changing_counts` | Count changes mid-video (2 squares 0–4s → 4 squares 4–8s); reported per half, so no single frame shows both answers. |
| `changing_text` | On-screen text changes (`ALPHA` 0–4s → `BRAVO` 4–8s); events at the window midpoints, 1.0s tolerance. |
| `rapid_events` | Six 0.3s flashes ~1s apart; tolerance is 0.5s, not 1.0s, so adjacent flashes are not blurred together. Stresses sampling density: a missed flash is a miss. |
| `negative_control` | Static black video, `expected.events == []`. Any predicted event is a false positive by construction — this is the honest false-positive-rate measurement. |

## Metrics

Pure functions in `suvix.evaluation.metrics`, each documented with its
formula and limitations. Undefined stays undefined (`None` — never
silently zero):

- **Structural:** JSON parse success rate, schema pass rate, missing
  required field rate, invalid evidence reference rate.
- **Semantic:** event precision/recall/F1 (greedy type+timestamp matching
  within tolerance), object count accuracy (binary, exact match),
  visible-text accuracy (normalized exact match), timestamp MAE,
  **timestamp bias** (signed mean error, pred − expected, over the same
  matched pairs as MAE), duplicate event rate, unsupported claim rate.
- **Tolerance sensitivity:** `event_metrics_by_tolerance` reports P/R/F1
  at several tolerances in one call, so the effect of the tolerance choice
  is measured instead of assumed (see below).
- **Operational:** end-to-end latency, provider request count (recovery
  calls included — §16.3 requires counting every model call), failure rate.
- **Economic:** total estimated cost, cost per correct event — only from
  measured/estimated usage; unknown stays `None`.

### Timestamp bias and tolerance sensitivity (experiment additions)

- `timestamp_bias` — the **signed** mean error (predicted − expected) over
  the same matched pairs as MAE. MAE alone cannot distinguish random error
  from systematic drift (the TGB study, see
  `docs/research/EXPERIMENT_RESEARCH.md`); a bias near ±the MAE means the
  extractor is consistently early or late, which is a different defect than
  noise. Report both.
- `event_metrics_by_tolerance` — precision/recall/F1 recomputed at several
  tolerances. The matching tolerance is a free parameter and the choice can
  swing conclusions; a result stated at one tolerance only is incomplete.

### Matching limitation, measured

Event matching is greedy (ascending |Δt|, each event consumed once) — an
approximation to optimal assignment, kept deliberately (documented,
dependency-free). The divergence is real and measured in
`tests/unit/test_oracle_benchmark.py`: predictions at 1.4s/1.6s against
expected events at 1.0s/2.0s with tolerance 0.55s — greedy scores
precision/recall 0.5 (it consumes 1.0s with the 1.4s prediction, stranding
1.6s), while the optimal assignment scores 1.0. On realistic,
well-separated events the two agree; on dense clusters greedy can
understate quality. Treat dense-cluster scores as lower bounds.

### Two-axis reporting

Following Video-MME-V2's methodology, quality numbers are only half a
result: every baseline entry in a run also records the resources consumed
(`frames_sampled` — from the selected-frame plan, `0` for native runs —
plus provider request counts and latency above), so a strategy that wins
by consuming more is visible as doing exactly that.

## Oracle validation pack (offline, no provider)

`benchmarks/tasks/` includes synthetic tasks whose ground truth is known
by construction (generated by `benchmarks/fixtures/generate.py`, never
labeled by a model): the original three plus `changing_counts` (object
count changes mid-video), `changing_text` (on-screen text changes),
`rapid_events` (0.25s flashes ~1s apart — stresses sampling density), and
`negative_control` (static video, expected events `[]` — measures the
false-positive rate; any predicted event is definitionally wrong).
`tests/unit/test_oracle_benchmark.py` drives the metrics with a perfect
oracle adapter and with controlled-noise variants (known timestamp jitter,
known drop/duplicate/hallucination rates, a known schema violation) and
asserts the computed metrics equal the known values exactly. This validates
the *evaluation machinery* offline; it says nothing about any real
provider's accuracy.

## Cost estimation

Suvix registers **no pricing by default**. `resolve_pricing(provider, model)`
returns `(None, "unavailable", "unverified")` until you register your own:

```python
from suvix.evaluation import cost
cost.register_pricing(
    provider="gemini", model="gemini-2.5-flash",
    table={"input_per_1k": 0.0003, "output_per_1k": 0.0025},
    source="https://ai.google.dev/gemini-api/docs/pricing (verified by me)",
    date="2026-10-15",
)
```

One opt-in exception: `cost.load_verified_pricing_snapshot()` registers
the Gemini 2.5 Flash / Pro (≤200k tier only) / Flash-Lite prices verified
against https://ai.google.dev/gemini-api/docs/pricing on 2026-10-23.
Nothing is registered until you call it.

Per-token tables cover token billing only. Video/second or per-image
components are not modeled — record them in the run's
`unestimated_components` rather than folding them into a fake per-token
number. Every benchmark report records the pricing `source` and `date`.

## Timestamp bias: drift is not noise

MAE discards the sign of every error, so it cannot distinguish a model
that is *consistently* 0.3s late from one whose errors are ±0.5s of random
jitter — yet the first is a systematic defect (clock offset, frame-rate
mismatch, drift that grows with position in the video) and the second is
noise. `timestamp_bias` keeps the sign: mean(pred − expected) over the
matched pairs. Read the pair together:

- MAE ≈ |bias| → the error is mostly systematic drift; find the cause.
- bias ≈ 0 with a large MAE → symmetric noise; more samples may help.
- bias growing with temporal position → drift, not a constant offset.

Like MAE, bias is `None` when nothing matched, and unmatched events are
invisible to it — never read it without recall.

## Tolerance sensitivity: report the sweep, not a point

P/R/F1 depend on `time_tolerance_seconds`, and the matching standard can
swing conclusions (different tolerances can rank the same systems
differently). Tolerance-window matching is accepted practice when the
tolerance is reported — so report it, and preferably report the sweep:
`event_metrics_by_tolerance(pred, exp, tolerances=[0.1, 0.5, 1.0])`
returns `(precision, recall, f1)` per tolerance. A result quoted at a
single tolerance is a claim about that tolerance, not about the system.
`rapid_events` ships with a 0.5s tolerance precisely because its ~1s
event spacing makes a 1.0s window meaningless.

## Two-axis reporting: quality AND consumption

A quality number without its cost axis invites the wrong conclusion (the
Video-MME-V2 lesson: report quality alongside the frames/cost consumed to
reach it). Suvix already records both axes per run — no extra work is
needed, but both must be quoted:

- **Quality axis:** the semantic/structural metrics above.
- **Consumption axis:** `BaselineResult.metrics` carries
  `provider_requests`, `recovery_requests`, `sampled_frames`,
  `latency_seconds`, and `estimated_cost_usd` (from the run's usage
  report) for every baseline, and `summarize()` keeps each as its own
  per-baseline mean.

Never present one axis without the other: "F1 0.9" from baseline D
(2 requests, 5 frames) and from baseline B (1 request, native video) are
different engineering results.

## Matching limitation: greedy is not optimal (measured)

Event matching is **greedy**: candidate pairs are consumed in order of
increasing time difference. Greedy can provably underperform the optimal
assignment. Measured divergence case (pinned in
`tests/unit/test_oracle_benchmark.py::TestGreedyVsOptimal`, optimal
computed by brute force inside the test): predicted events at 0.5s and
−0.6s, expected at 0.0s and 1.1s, tolerance 1.0s. Greedy takes the single
closest pair (0.5↔0.0) first and blocks both remaining candidates →
**1 match, recall 0.5**. The optimal assignment (0.5↔1.1, −0.6↔0.0) →
**2 matches, recall 1.0**. Real predictions with dense, near-coincident
events can therefore be under-scored by the harness itself. This is a
known, measured limitation of the metric, not a hidden one; an
optimal-assignment matcher is future work, and until then dense-event
scores should be read with this gap in mind.

## Oracle validation: the machinery, proven against known answers

Before any provider number is trusted, the harness must prove it recovers
*known* values. `tests/unit/test_oracle_benchmark.py` does this offline: a
test-local oracle adapter returns a task's expected output verbatim — or
with a controlled, hand-computed distortion — through the real runner.
Assertions that now hold exactly:

- perfect oracle → precision = recall = F1 = 1.0, MAE = 0.0, bias = 0.0,
  duplicate rate = 0.0, schema pass = 1.0;
- every timestamp shifted +0.3s → MAE = 0.3, bias = +0.3, all events still
  matched (F1 stays 1.0);
- every second event dropped (6 → 3) → recall = 0.5, precision = 1.0;
- every event duplicated → duplicate rate = 0.5, precision = 0.5;
- 2 hallucinated events added to 2 real ones → precision = 2/4 = 0.5;
  on `negative_control`, hallucinated events score precision = 0.0 and
  unsupported-claim rate = 1.0;
- the schema-required `events` field removed → schema pass rate = 0.5
  across one perfect and one broken result.

This is **offline pipeline validation only**. The oracle reads the answer
key by construction, so these tests say the *machinery* tells the truth —
they say nothing whatsoever about any provider's accuracy.

## Interpreting results

- Read `summarize()` output per baseline and per metric. There is no
  "winner" field and no total score — by design (§16.1).
- If Suvix doesn't beat the raw provider on accuracy, that is a result,
  not a failure: §16.7 explicitly allows Suvix's value to be validation,
  evidence traceability, consistent contracts, and reduced integration
  work — described accurately, not as accuracy gains.
- Timestamp MAE without recall is meaningless; cost without a pricing
  source/date is not a cost. The report files keep both attached.

## Honesty rules (non-negotiable)

1. No invented baselines — skipped baselines are recorded, not faked.
2. No invented prices — unknown cost stays `"unavailable"`.
3. No invented usage — missing provider values stay `None`.
4. No collapsed scores — trade-offs stay visible.
5. Negative results are retained and reported (§16.7).
6. Benchmark outputs are written **only** when you pass `output_dir`
   explicitly (§16.6). The library keeps no benchmark history.

## What this harness can and cannot do yet

**Can:** define tasks, run baselines A–E against any adapter (the
deterministic fake adapter makes the whole loop testable offline),
compute every §16.4 metric as pure functions, record fair-comparison
notes, summarize per-baseline tables, document cost basis honestly, and
prove the metrics recover known values via the oracle pack (above).

**Cannot (no provider keys here):** establish any real baseline numbers
or verify real-provider usage metadata shapes. Any accuracy or cost claim
made before real runs is, by the project's own rules, not a claim at all.
